# DanyWhere roadmap

Planned work on DanyWhere, roughly in priority order within each section. Items that would benefit every Handy user are marked **upstream candidate** and are offered to [Handy](https://github.com/cjpais/Handy) as well. Since 2026-11-22 DanyWhere no longer merges Handy as a whole but takes over useful changes one by one, so its designs and texts can go their own way.

## Features and improvements

### Inserting on macOS: an input method of DanyWhere's own

**Found (user, 2026-11-23, in 0.3.1 on the company Mac):** without Accessibility an end shortcut ends the recording but can't insert (the text waits for the "Insert Last Dictation" service), and a key press in Append is dropped. The input method set aside on 2026-11-11 (see "Running without the Accessibility permission") was tried there with a small test app, the pre-release `eingabe-test-1` of this repository: installing it in the user's folder, selecting it with the keyboard layout kept, inserting into another app and inserting right before an Enter that still reaches the app all worked. Enabling it by a program call (`TISEnableInputSource`) answers success but enables nothing, also on an unmanaged Mac, so the user adds it once in System Settings.

**Decided (user, 2026-11-23):** the input method becomes macOS's general way of inserting, by one rule on what the Mac can do instead of two modes: (1) once the DanyWhere input source is added, DanyWhere inserts through it, with or without Accessibility, without the clipboard; (2) else, with Accessibility, by ⌘V as today; (3) else the text waits as today without Accessibility. Only setups without Accessibility are guided to add it; with Accessibility it is offered in the settings ("insert without the clipboard"), and nothing changes for those who don't. DanyWhere selects its input source only while a dictation runs, keeps the keyboard layout in use, and switches back afterwards. Enter as an end shortcut inserts the text and then lets Enter through ("insert and send"). Key presses DanyWhere would have to generate itself still need Accessibility; with both, the input method inserts and Accessibility presses the key. Shortcuts and window titles stay as they are. The code diverges at one point, how a text is inserted; the dictation flow stays the same. To be planned and built right away, test-first.

There is no GitHub Pages site and no wiki.

**Claude's proposal (not decided):** one source in Markdown, in English and German, built with Astro Starlight into a site that is published on GitHub Pages and also bundled into the app, where a window of its own shows it offline and matching the installed version. Diagrams in PlantUML and Graphviz, rendered to SVG in DanyWhere's colours; screenshots generated from the real interface with Playwright and the component tests' mocks, in every language and appearance and without private data. A "Manual" entry in the sidebar and the tray, a "?" on each settings page and a "Learn more" on each notice open the matching chapter; tests check that every such link has its chapter. The README shrinks to a pitch, installation and a link. A prototype with two chapters comes first, so the look and the tone can be judged before everything is written; the chapter on inserting waits for the input method above.

**Decided (user, 2026-11-24):** as proposed: one source for the website and the app; in English, German, Spanish and French (the app's other languages show the English manual); screenshots generated automatically; the README shrinks once the manual is online. The prototype starts now, next to the input method.

**Built (2026-11-24, on `feat/manual`):** a Starlight site in `docs/manual/` (its own `package.json`; every app build runs `build:manual` into `public/manual/`, `build:manual:web` builds the website), a style guide with a glossary in four languages (`docs/manual/STYLE.md`), a landing page and three chapters in English, German, Spanish and French ("A dictation from start to end", "Start and end shortcuts", "Defaults and profiles"), four diagrams in PlantUML and Graphviz checked against the code (`docs/manual/diagrams/`, light and dark, `render.sh --check`), and four pictures of the interface generated from the real React UI with made-up data (`bun run manual:screenshots`, vector SVG with open fonts). In the app the manual is a page of the main window, between History and About, showing the site in a frame in the interface language; a "?" next to End Shortcuts and on the profile pages opens its chapter; links to websites open in the browser; the page follows Application Theme. The Nix package builds without the manual for now (its sandbox can't install `docs/manual`'s own lockfile).

The outdated description of the second start shortcut (out of the box on macOS it no longer post-processes) and README step 4 are corrected before that release. Handy: DanyWhere introduces itself on its own; its origin and thanks get a section of their own at the end of the README ("Origin and thanks"), a page "About DanyWhere" in the manual, and on the app's About page "Grown out of Handy" with a sentence of thanks and the link; the statement that Handy's makers are neither involved nor responsible stays.

### Notices: a failed post-processing says why

**Found (user, 2026-11-23, in 0.3.1):** Enter and Ctrl+Enter, the end shortcuts with post-processing, pasted the transcript as is, and the notice "Pasted Without Post-Processing" said only that post-processing didn't finish. The cause was in the settings: the profile In Use sent post-processing to a local model that had been removed from Ollama. Only the log said so (`404 … model '…' not found`).

**Decided (user, 2026-11-23):** the notice names the actual reason, so the user knows what to change, without a full diagnosis. Examples: the provider doesn't have the model, the API key is missing or refused, the provider can't be reached or didn't answer in time. Nothing else changes; Claude's further proposal, a warning on the Post Process page for a model the provider no longer lists, isn't wanted. **Not on its own: built along with the next code change.**

Where: `PostProcessOutcome::Failed` (`src-tauri/src/actions.rs`) carries no reason, and `pasted_dictation_notice` (`src-tauri/src/dictation_flow/mod.rs`) raises `PostProcessFailed` without `with_detail`; the text comes from `NOTICE_DISPLAY` (`src/lib/notices.ts`). Claude's recommendation: give the post-processing of History entries and files (`HistoryPostProcessFailed`, `FilePostProcessFailed`) the same reason, since they fail the same way.

**Built (2026-11-23, ships with 0.3.2):** `PostProcessOutcome::Failed` carries a `PostProcessFailure` (`src-tauri/src/post_process_failure.rs`): no provider, no model, no prompt, no API key, a refused key, a model the provider doesn't have, not reachable, no answer within the time limit, another HTTP status, an empty or cut-off answer, Apple Intelligence not available, or the raw error. The notices of a dictation, of a History entry and of a file get it as a small JSON detail, and `src/lib/postProcessFailure.ts` adds one sentence after the explanation, naming the provider and the model, e.g. "Custom doesn't have the model “gemma4-12b-qat”." (German: „Der Anbieter „Eigener Anbieter“ kennt das Modell „gemma4-12b-qat“ nicht."); without a readable detail the notice says what it said before. All 26 locales.

### Post-processing: several prompts, chained or as alternatives, chosen and ordered per profile

**Idea (user, 2026-11-18; to be discussed next):** there can still be several post-processing prompts, but they are no longer alternatives to each other: the user decides which of them run and in which order, so they can be chained or used as alternatives, every combination. The order is set by drag and drop or by numbers, best both. The prompts exist in every profile; which of them a profile uses, and in which order, belongs to the profile.

**Decided (user, 2026-11-18):**

- One shared prompt library instead of a copy per profile; a profile stores only which prompts are active and their order. A change to a prompt applies wherever it is active; a variant for one profile is a duplicate under a new name. On the first start, identical prompts become one, and different texts under the same name become separate prompts named after their profile, each profile keeping the prompt it uses today (Claude's proposal, not objected to).
- The library is an editable list like the History's entries: each prompt shows part of its text in a scrollable box that opens for editing, and entries can be moved (dragged, plus number and arrow keys). The checkbox is called "Active".
- If prompts ever run in more than one request, model and effort can be set per request.

- All active prompts go into one request, in their order, each under its name; the frame tells the model that they apply in turn and that a later one wins where two contradict. A prompt that still contains `${output}` can't be combined: while it is active it runs alone, as today, and the startup warning says so. A new prompt is active in no profile until checked; numbers go to active prompts only; each profile keeps the order of the whole list (Claude's recommendations, accepted by the user).

**Wanted later (user, 2026-11-18; a few things to settle first):** cutting the list into several requests. The list stays one row; a switch "new request" between two active prompts ends a request there, and the next one gets its result instead of the transcription. Without a cut this is the single request above, so it can be added without migrating anything. Still to settle then: what a later request's frame says (Claude: no "correct misheard words", context still sent), the time limit per request, how its versions show in the History, and what is inserted when a later request fails (Claude: the last good result, with a warning).

**Built (2026-11-19 to 2026-11-22, ships with 0.3.0):** the prompts are one library shared by all profiles, shown on the page Post Process of the defaults and of each profile as a list: every prompt has its name, part of its text in a scrolling box that opens the editor on a click, a checkbox "Active" and, while active, its number in the order the active ones run. A prompt moves by dragging its grip, or with ↑ and ↓ while the grip has the focus; Escape cancels a drag. Which prompts are active and the order of the whole list are a value of the defaults that a profile follows until its order or a checkbox is changed there; the profile then keeps the whole order as its own, not prompt by prompt. Editing a prompt's text changes it for every profile, and deleting a profile leaves the prompts. A new prompt goes to the end and is active nowhere, a new installation has none active (as in Handy), a name another prompt has is refused with a notice while typing, deleting a prompt that is active somewhere first names those profiles, and the last prompt can't be deleted. All active prompts go to the model in one request, in their order, each in `<instructions>` tags with its name; the frame says that several sets apply in turn and that the later one wins where two contradict, and a single active prompt goes as its text alone, as before. An active prompt that still contains `${output}` runs alone (the first such) and the other active ones are left out; the list says so at that prompt, and the startup warning about such prompts now always adds it. Without an active prompt a dictation gets its transcript, as before without a selected prompt, and the list warns. History's step names every prompt of a post-processing, joined by "→". The first start merges the profiles' copies into the library: the same text becomes one prompt under the name it had first, the prompts of the profile "Default" keep their names, another text under a name already taken becomes "<name> · <profile>", and every profile has exactly the prompt it used active, so the same text goes to the model as before. An exported profile carries the texts of its active prompts; an import reuses a prompt with the same name and text, adds one with another text as "<name> · <profile>" and never overwrites one, and a file from before the library brings all its prompts, its selected one active. Not as decided: the numbers only show the order, typing one doesn't move a prompt.

### History: post-processing always adds a version on top

**Idea (user, 2026-11-18; to be discussed next):** today, post-processing a lower version first deletes the versions above it. That isn't necessary: whichever version is post-processed, the result always goes on top of the stack, which is also simpler to use. So that the stack doesn't grow too large when an entry is post-processed often, single versions could be deleted, at the bottom, at the top or in the middle, except the transcription itself (or except the recording; still to be thought through).

**Decided (user, 2026-11-19):** one rule for everything that makes a version: post-processing, the user's own edit of a lower version and re-transcribing all put their result on top, and nothing is deleted on the way (re-transcribing keeps the old transcription below; this part is Claude's idea). Changing a version in place ("Save") is offered only on the top one. No limit per entry.

**Decided (user, 2026-11-19, later):** all versions are alike: they can be moved up and down freely (dragged in the track, or "to the top", "up", "down" in a version's menu) and deleted, the original transcription included, as long as one version is left; the top one is the entry's result. Deleting the transcription clears its own database column too. Deleting never asks. The wand's "replace" and "redo from the previous version" go; a click applies the profile's active prompts to the shown version and puts the result on top.

**Decided (user, 2026-11-19, last):** a version doesn't remember which one it came from; its steps (who, when, which prompt) stay. The wand's menu lists every prompt of the library by name, in the profile's order with the active ones checked, the full name and the text's first lines in a tooltip; choosing one applies only that prompt to the shown version and puts the result on top. Prompts that aren't active in the profile are offered too. With the shared library, prompt names are unique (Claude's proposal): saving under a name already taken is refused with a notice.

**Built (2026-11-19 to 2026-11-22, ships with 0.3.0):** ✨, saving an edit of a lower version and re-transcribing all put their result on top and delete nothing, without asking; a result equal to the top version adds nothing (after ✨ a short notice says so), one equal to another version is added all the same. A lower version offers only "Save as New Version"; the top one also "Save", which now changes even a transcription in place (kept by the user, 2026-11-22), and ⌘↩ still saves a new version unless the user made the last step. Re-transcribing keeps the old transcription below the new one; only an empty one (a file not transcribed yet, a failed transcription) is replaced. As in Handy, a plain "Re-transcribe" also post-processes the new transcript when the entry was post-processed before; its tooltip now says so ("Re-transcribe and post-process again, as before"). Versions are dragged to any place in the track (Escape cancels), and the current version's menu "…" has "Move to the Top", "Move Up", "Move Down" and "Delete the Current Version", for every version, the transcription included, as long as one is left, and never asks; "Move to the Top" takes the place of going back to a version and moves it instead of deleting the ones above. Versions no longer record which one they came from, only their steps; the arrows between the chips show the order from bottom to top, and the last chip's tooltip calls it the entry's result. A deleted version is gone from the database, so the search no longer finds it; once the transcription is deleted, the column that held it keeps the latest remaining transcription, or the top version's text when none is left, because Handy's code takes an empty transcription for an entry without text. A click on ✨ post-processes the version shown with the active prompts of the profile in use; the arrow next to it opens "Post-process with", every prompt of the library by name in that profile's order, the active ones marked, long names cut with "…", the full name and the text's first lines in a tooltip, and choosing one post-processes the version shown with that prompt alone, even when no prompt is active. The wand's "replace" and "redo from the previous version" are gone. Existing entries keep their versions and change to the new storage when next changed; an older DanyWhere shows such an entry with only its transcription and last post-processing. Not as decided: the redo for the application a dictation goes into (0.2.1) still replaces the dictation's own transcription or post-processing instead of adding on top, as long as the entry is exactly as the dictation made it (kept by the user, 2026-11-22); an entry whose versions were moved, deleted or added is pasted as it is, and only what is appended follows the target's profile.

### Shortcuts: start per profile, end with what follows

**Idea (user, 2026-11-18; to be discussed next; picks up the finishing keys still open under "Append any text, and actions per finishing key"):** a recording starts with a shortcut of its profile. It ends with one of several shortcuts, each set up with (1) what is appended, (2) whether the text is post-processed, (3) whether the context from earlier dictations goes along. Then the context would need no switch of its own any more; the user isn't sure about the third point yet.

**Decided (user, 2026-11-19):** the start shortcut is a value of the profile and doesn't choose the profile. The profile is chosen as before (the application in front, or the profile fixed by hand), and there only that profile's start shortcut starts a recording; the start shortcuts of other profiles have no effect there and reach the application. Profiles may share a start shortcut, and usually all will; a profile gets its own only where the user wants one.

**Decided (user, 2026-11-19, later; Claude's recommendations):** start and end shortcuts are ordinary settings with a default that a profile can override (see the next entry), the end shortcuts entry by entry. Every end shortcut has a name and three values: what is appended, whether the text is post-processed (with the profile's active prompts; choosing prompts per shortcut may come later), and whether the context goes along. Every start shortcut has a default end, used by its second press and by its release when held: ⌃Space ends "Plain", ⌃⇧Space stays a start shortcut and ends "Post-process". Out of the box only these two end shortcuts exist, with the Append text and the context the profiles have today; more (e.g. ⌃↩ with Enter, ⇧↩ with a new line) are the user's to add. End shortcuts are registered only during a recording, like Escape. After switching applications during a recording, the shortcuts of the profile that applies now count. The context hangs on the end shortcut alone: "Send Context" as a profile value, its shortcut ⌃⇧X, its tray item and its switches go. Without Accessibility every profile uses the default shortcuts, a profile's own shortcuts and additional end shortcuts work only with Accessibility (the settings say so), and the three services stay as they are.

**Parked (user, 2026-11-19, while building):** the mode without Accessibility is left out for now. The new shortcuts, and the other new features, are built for the normal case with Accessibility; the existing mode without it stays as it is, and what is possible may be carried over later.

**Built (2026-11-19 to 2026-11-22, ships with 0.3.0):** every shortcut is a profile value, entry by entry, the two start shortcuts as well as the others, and DanyWhere registers only those of the profile that applies now, so the others reach the application: they follow a change of the profile in use, fixing it, "Choose Profile by Application", and on macOS every application that comes to the front (Windows looks every 300 ms; on Linux they follow only the profile in use). The page General of the defaults and of every profile has a group "End Shortcuts" after the shortcuts: for each start shortcut "Default End of …", which its second press and its release when held use, and the list of end shortcuts, each with a name, a shortcut of its own or none, the "Append" text and key press with their preview, "Post-process" and "Send Context" (only with post-processing), and "Add End Shortcut". Out of the box there are "Plain", ⌃Space's default end, and "Post-process", ⌃⇧Space's; the first start gives both, in every profile, the "Append" text and the "Send Context" the profile had, and "Append" is gone from Advanced → Output. An end shortcut's combination is registered only while a recording runs, like Escape, and ends it whether tapped or held; after switching applications during a recording, those of the profile that applies now count. Another start shortcut ends a locked recording only when its default end post-processes and the recording's doesn't, as before. A combination another shortcut or end shortcut has is refused, and an end shortcut a start shortcut ends with by default can't be deleted. "Send Context" as a profile value, ⌃⇧X, the tray item and the switches in the sidebar and on Post Process are gone; the overlay's speech bubble shows at the start whether the start shortcut's default end sends context, at the end what the end shortcut used decided. History remembers the end shortcut: inserting into an application with another profile uses that profile's end shortcut with the same id, else the one used, and "Paste Last Transcript" and "Copy Last Transcript" outside a dictation append what the last dictation's end shortcut appends, after a restart what the dictation shortcut's default end appends in the profile in use. On Linux the end shortcuts' own combinations aren't taken, and the settings say so. Limits: Escape and the activation mode (toggle or push-to-talk) are profile values too but come from the profile in use, so a profile's own value for them counts only while it is in use; prompts per end shortcut are left for later, as decided. Not built, with the mode without Accessibility parked: there the shortcuts follow the profile as well instead of using the defaults, the services get the start shortcuts of the profile in use, and the settings don't say that a profile's own shortcuts need Accessibility. Since then (2026-11-22): a combination with a main key is recorded and stored without a side, so the left or the right Ctrl, Option, Shift or Command fires it; a combination of modifiers alone keeps its side, and so does Alt off macOS, where the right Alt is AltGr. Stored combinations lose their sides when the settings are read, in the defaults, every profile and an import; where two would then be the same, an end shortcut that never fired on its own loses its combination and keeps its entry, so nothing that fired before stops. The duplicate checks count two combinations as the same when one press fires both. Combinations show as the system names them: on macOS with the symbols on the keys ("⌃⌥D", "⌃↩"), on Windows and Linux with the translated names joined by "+" ("Strg+Umschalt+V"), and the paste method says "Clipboard (⌘V)" or "(Ctrl+V)". Onboarding's keycaps and the key presses of the "Append" field use the same names ("⌥ Leertaste", "⌘↩", "Strg+Eingabe").

**Rethought (user, 2026-11-22):** the two built-in end shortcuts "Plain" and "Post-process", each the "default end" a start shortcut picks from the list of end shortcuts, mixed two things up; that came from Claude's recommendation of 2026-11-19, not from the user's wish. The new concept: start shortcuts only start, end shortcuts only end, and the two have nothing to do with each other (changing a start shortcut never changes an end). Ends are a free list and none of them is distinguished, with no fixed name; each has its own combination and says what is appended, whether the text is post-processed and whether context goes along. The defaults have at least one end, and a profile overrides ends and adds others, so there is always a way to end. Pressing a start shortcut's combination during a recording ends it only when an end has that combination; out of the box ⌃Space and ⌃⇧Space are ends too, so nothing changes in use. The one exception is holding: releasing a held start shortcut ends the recording as configured for holding. Decided later the same day (user): holding is configured per start shortcut as an end of its own (what is appended, whether the text is post-processed, whether context goes along), without a name or a combination, next to the activation mode; out of the box ⌃Space held ends without and ⌃⇧Space held with post-processing, as today. Every end has a name, prefilled with its key combination as the shortcut fields write it ("⌃↩"); it can be changed but needn't be. Proposed by Claude and confirmed by the user: as long as no name of one's own was typed, the name follows the combination and the interface language, and the field shows it as plain text under a visible label "Name".

**Built (2026-11-22, ships with 0.3.0):** start shortcuts only start, and ends are a free list, as decided. Every end needs a key combination; two ends can't share one, and an end may have exactly a start shortcut's combination: pressing that start shortcut during a recording, its own second press or the other one's, held or locked, then ends that way, and a start shortcut whose combination no end has does nothing during a recording. "Default End of …" and the rule by which another start shortcut ended a recording only when its end post-processed and the recording's didn't are gone. "When Held", under "Shortcut Behavior" and shown unless that is "Toggle", gives each start shortcut its hold end ("Append", "Post-process", "Send Context"), one profile value as a whole (`hold_ends`). An end's name shows its combination ("⌃↩") as long as no name of its own was typed, as plain text under the label "Name"; "Add End Shortcut" records the combination first and adds nothing without one. The last end of the defaults or of a profile can't be deleted or switched off, neither by deleting an entry of the defaults that a profile follows alone; on Linux, where the ends' own combinations aren't taken, a change that would leave no way to end (an end with a start shortcut's combination, or "Hold") is refused. Out of the box and on the update from 0.2.5: the ends ⌃Space without and ⌃⇧Space with post-processing, holding the same, each with the "Append" text and the context the profile had; from Dev, the default ends became the hold ends and took the start shortcuts' combinations, and ends without a combination went (Dev had none). The start shortcuts are called "Start Shortcut" and "Second Start Shortcut"; the second stays on Post Process and is taken only while post-processing is reachable, as before. Remote control, the services and Handy's stop end as a press of their start shortcut would, else with its hold end; where no end is known ("Paste Last Transcript" after a restart), the end with the first start shortcut's combination applies, else its hold end. Overlay and History name no end, so "⌃Space held" shows only on the page Profile and under the defaults. Not built, with the mode without Accessibility parked: nothing of its own; its services end as a press of their start shortcut would. Since then (user, 2026-11-23, ships with 0.3.1): the second start shortcut is on General, under the first, and still taken only while post-processing is reachable; "When Held" shows it only then, and the group "Hotkey" on Post Process is gone.

### Shortcuts: the user's end shortcuts as the factory ones

**Decided (user, 2026-11-24):** the end shortcuts the user set up in the release on 2026-11-23 become a new installation's: one rule for all twelve, ⌥ (Option) post-processes, ⇧ picks the smaller variant, ⌃ on Enter presses a key instead of appending text; first the six without post-processing (⌃Space a space, ⌃⇧Space nothing, ↩ two line breaks, ⇧↩ one, ⌃↩ `{Enter}`, ⌃⇧↩ `{Shift+Enter}`), then the same six with ⌥ and post-processing. Without Accessibility, the ends that press a key are left out, as DanyWhere can't press keys there, not even with its input method. Assumed by Claude, to be confirmed: macOS only (Linux takes no end's own combination, and on Windows Ctrl+Alt is AltGr), "Send Context" exactly where an end post-processes, and both hold ends appending a space, the second with post-processing.

**Built (2026-11-24, not released):** `end_keys::factory_end_keys_on` gives macOS the twelve ends (ids `direct_*` and `post_*`, no names of their own yet) and Windows and Linux the two built-in ones as before; `factory_hold_ends_on` gives macOS hold ends with a space. "Continue without Accessibility" drops the four ends with a key press while the list is still the factory one (`end_keys::drop_factory_key_presses`); the defaults and the profiles following them get the same through `route_flat`, and a list of the user's own stays as it is. Existing installations change nothing: a store without end shortcuts still reads the two built-in ones (`stored_before_end_keys`) until `migrate` carries its values over. Found on the way and fixed: the Tauri shortcut backend, used without Accessibility, couldn't parse a combination with Return as handy-keys' recorder writes it (`return`), so an end with ↩ couldn't register there (seen in the parser's error, not tried on a Mac); it now reads `return` as `enter`.

**Decided (user, 2026-11-24, "Variante 2"):** the factory ends get names, written once in the language of the new installation; from then on they are names like typed ones and follow neither a change of language nor a changed end. Chosen over names DanyWhere would derive from what an end does, which would have followed both, because it is consistent with the user's own German names.

**Built (2026-11-24, not released):** a factory end's name is "mode · effect" from `settings.endKeys.factoryNames` in every locale (a pattern with `{{mode}}` and `{{effect}}`, the two modes and six effects); German gives exactly the user's names ("Direkt · Leerzeichen" … "Nachbearbeitet · Shift-Enter senden"), English "Direct · Space" … "Post-processed · Send Shift+Enter". build.rs carries the words into Rust beside the tray's strings (`factory_end_name_*`), and `end_keys::FactoryEndNames::for_locale` finds them for the system's locale as the tray does (`de-AT` → German, an unsupported one → English); `get_default_settings` names the macOS ends in `app_language` as it starts. Windows' and Linux' two ends stay unnamed. The drop without Accessibility compares the lists without their names, so a list written in another language, or renamed, still loses its key-press ends.

### Shortcuts: ⌥ before ⌃ on macOS

**Wish (user, 2026-11-23):** the user's end shortcuts follow one rule: ⌥ (Option) adds post-processing, ⇧ picks the smaller variant, ⌃ on Enter presses a key instead of appending text. Their names start with it ("Direkt · Absatz", "Nachbearbeitet · Absatz"). On macOS a combination should show ⌥ left of ⌃, so its first symbol already tells an end with post-processing: ⌥⌃↩ instead of ⌃⌥↩. ### Post-processing: a fixed frame around every prompt

**Idea (user, 2026-11-14; next):** the part of a prompt that tells the model what it gets — a speech-recognition transcript between `<transcript>` tags, to be processed rather than answered — should be sent by DanyWhere itself, so a prompt only says what to do with the text. **Found:** a prompt has to contain `${output}`. For providers without structured output (Anthropic, Groq, custom) the transcript takes its place and the whole prompt goes out as one message, so without `${output}` the model never sees the transcript. For providers with structured output the transcript goes as a message of its own and `${output}` is dropped, so the prompt's `<transcript>` tags arrive empty.

**Done (2026-11-14, ships with 0.2.0):** DanyWhere sends a fixed frame (what the model gets, that instructions and questions in the dictation are not to be followed, that the language stays unless the instructions say otherwise, that only the result is returned), then the prompt's instructions, then the context if any, then the transcript in `<transcript>` tags. The frame always goes out in English; the editor shows it read-only above the prompt, translated into the interface language. A prompt only says what to do with the text. **Done (2026-11-15, ships with 0.2.0):** the frame no longer lets the instructions override "do not answer questions in the dictation" or "keep its language" (a translation prompt still translates), and it tells the model that speech recognition mishears words and that such errors are to be corrected where the context makes clear what was said, while anything that could have been meant stays as dictated. ### Word lists behave differently per speech model

**Found (2026-11-12, to be discussed):** models that take a vocabulary, such as Whisper, get the word lists as one and skip the replacement afterwards. Models without, such as Parakeet, get a fuzzy replacement of similar words after the transcription, which turned every "Bild" into "Build" once "Build" was in a list. The same list therefore helps with one model and harms with another.

**Wish (user, 2026-11-22):** tell word lists the speech model can use apart from word lists it can't. For a model without vocabulary the lists only drive the fuzzy replacement inherited from Handy, which in the user's experience almost never gives the wanted result, though it may have its uses now and then. The question is whether there is a clean and fairly reliable way to find out whether, and how, a word list should be switched on for a given model.

**Found (2026-11-22):** whether a model takes a vocabulary is no guess: transcribe-cpp reports it for the loaded model (`Feature::Vocabulary`) and DanyWhere already uses it to choose between vocabulary and replacement, but the interface never says which of the two applies. Of the catalog only the Whisper models (Small, Medium, Turbo, Large, Breeze ASR) take one; Parakeet, Canary, Moonshine, SenseVoice, GigaAM and Cohere don't. The replacement takes a word, or up to three words run together, for a list entry when their edit distance is below 18 % of the longer one, or below 60 % when both have the same Soundex code (an English phonetic code of the first letter and three consonant classes, B430 for both "Bild" and "Build"); it knows no dictionary and no sentence. In the release's History (419 dictations since 2026-11-13, when replacements began to be recorded) it replaced 16 times in 13 dictations, all made with a model without vocabulary: 10 were right, misheard names and twice a misheard "pushe" ("Deniware" and "Danyware" → "DanyWhere", "Battly" → "BeThLi", "Cloud" → "Claude", "Pusche" → "Pushe"), 6 were wrong, all of them correct German words ("dann eher" and "dann nur" → "DanyWhere", "passe" → "pushe", "pushen" → "pushe", "committen" → "committe"). Post-processing with context, which names the replacements to the LLM, undid the wrong ones in all four dictations it ran on and kept the right ones; the one wrong replacement without post-processing went out as "dann pushe ich es an". Biasing during decoding would give Parakeet and Canary a real vocabulary (NeMo's phrase boosting works with greedy TDT and Canary decoding; sherpa-onnx and CrispASR have hotwords), but transcribe-cpp offers it for neither.

**Proposal (Claude, 2026-11-22, not decided):**

- Show per speech model whether it uses the word lists, on its card and on the word list pages.
- Keep what a list holds apart from how it is applied: entries say how a term is written; a model with vocabulary gets them as vocabulary, post-processing gets them as known terms (next section), and the fuzzy replacement becomes a switch of its own per profile.
- Replacement rules "heard → written" (e.g. "Deniware → DanyWhere"), applied exactly and with every model; History could offer one when the user corrects an entry.
- Let the fuzzy replacement, where it stays on, touch only words that are no word of the language (a spelling dictionary): that would have stopped most of the wrong replacements above, but also "Cloud" → "Claude".
- Measure per model and list: transcribe kept recordings again with and without the list and show only the places that differ (as the Whisper check of 2026-11-12 did with synthetic speech); for the fuzzy replacement, a view in History of what it replaced, where marking a pair as wrong makes it an exception.
- Later, perhaps: biasing during decoding for Parakeet and Canary in transcribe-cpp.

**Decided (user, 2026-11-22):** two first steps at once: store with every transcription which speech model made it, and switch the fuzzy replacement off. What follows, and when, is decided later.

**Done (2026-11-22, ships with 0.3.0):** Handy's fuzzy replacement no longer runs: a model without vocabulary keeps the text as it heard it, and the word lists reach only models that take them as vocabulary (the Whisper models). The "Word Correction Threshold" on the Debug page and its setting are gone (a stored value is read past), and the word list's description no longer speaks of a fuzzy correction, in all 26 languages. With Canary or Parakeet the lists therefore do nothing for now, also where the replacement used to be right ("Deniware" stays "Deniware" unless post-processing fixes it). When a profile is chosen again at the end of a recording, a different word list still makes it transcribe again, though for such a model the result is the same. Every History entry now records which speech model made its transcription, taken from the run itself (a new column `transcription_model`, replaced by every new transcription), and each version keeps the model of its transcription step, also after "Transcribe Again" with another model; History names it by its display name ("Transcribed with …") in the tooltip of the entry's date and of a version chip. Entries from before have no model and show as before.

**Decided (user, 2026-11-22):** stage 1 next and at once: show whether the speech model takes the word lists, and send the lists to post-processing as known terms, always (also behind Whisper and without "Send Context"). Exact replacement rules, a dictionary guard, measuring and biasing during decoding wait.

**Done (2026-11-22, ships with 0.3.0):** every model says whether it takes the word lists: before a load from its architecture as transcribe-cpp 0.4.2 decides it (Whisper, Qwen3-ASR and FunASR-Nano yes, Granite Speech by its header flag, MOSS only once loaded, all others no), after a load from the loaded model. The word lists' group under Advanced, for the defaults and in each profile, names the page's speech model and says either that it uses the word lists while it recognizes speech, or that it doesn't and post-processing gets them as known terms; the model table and the onboarding cards show "Word lists" as a capability, with a filter. Post-processing gets the word lists in effect after the instructions and before the context block, in a `<known_terms>` block that says what they are for, so the fixed frame stays unchanged. New strings in all 26 languages.

### Space between consecutive dictations

**Problem:** dictating into the same text field in several separate recordings (record, stop, record again) glues the pieces together: "…end of sentence.Next sentence…".

**Cause (inherited from Handy):** every recording is pasted on its own, with nothing before it and — unless the off-by-default setting "append trailing space" (`append_trailing_space`) is on — nothing after it. Within a single long recording there is no problem: the chunks of long-form transcription are joined with spaces (`join_transcripts` in `src-tauri/src/audio_toolkit/chunking.rs`, covered by tests; verified with a 60 s recording).

**Options:**

1. Turn on the existing trailing-space setting by default. Simple, but leaves a trailing space at the end of a field and before punctuation typed afterwards.
2. Look at the character before the cursor (macOS Accessibility: focused element's selected text range and the text before it) and prepend a space only when it is a letter, digit or sentence punctuation. Exact, but needs the Accessibility permission and is not supported by every app; fall back to option 3 or 1.
3. Remember the last paste (target app, time, last character) and prepend a space when the next dictation goes into the same app shortly afterwards and the previous one did not end in whitespace. Works without Accessibility; can be wrong if the cursor was moved in between.

**Proposal:** option 2 where available, option 3 as fallback (e.g. in "continue without Accessibility" mode); never add a space before text that starts with punctuation, and respect languages without word spacing (reuse `is_unspaced` from the chunk joiner). **Upstream candidate.**

**Deferred:** not before the first public release; the preferred behaviour is still open.

### Named word lists

**Problem:** there is one list of custom words for everything. Whisper models get the list as a short context ("Glossary: …") of at most 223 tokens (roughly 70–100 German words); what does not fit is dropped from the end. Parakeet and Canary have no such input; for them DanyWhere replaces similar-sounding words after transcription, and only for entries without umlauts or ß. One long list mixing topics therefore biases recognition less precisely than a short list for the topic at hand.

**Done:** the custom words are now the **Global Word List**, which always applies. Named additional lists (e.g. "Work", "Programming") are managed in the Advanced settings the same way as the post-processing prompts; one of them or none is switched on in addition. The model gets the additional list's words first, then the global ones. The shortcut ⌥⇧L steps through the lists (only global → first list → … → only global) and shows the result briefly in the overlay; the tray menu shows the active list and switches it.

### Phantom phrases at the end of a recording

Whisper sometimes appends text that was never said when the recording ends in silence (observed: "Vielen Dank." after a synthetic 60 s German recording). Known Whisper behaviour on trailing silence. To check: whether trimming trailing silence with the VAD before decoding (or dropping a final chunk without speech) avoids it.

### Translation to English

**Problem:** Whisper large-v3-turbo, DanyWhere's default model, cannot translate (it was fine-tuned on transcription data only). The legacy `ggml-large-v3-turbo.bin` still reports translation support, so "Translate to English" is offered, the log says "(translated)", and the text stays in the spoken language (reproduced 2026-10-24). DanyWhere lets the catalog's capabilities win (the GGUF Turbo is marked `translate: false`), so the option no longer appears for Turbo (verified 2026-10-26).

**Options:** translate with Whisper medium or small (trained for translation; both in DanyWhere's selection), or with LLM post-processing (a "translate to English" prompt; usually better quality, needs a provider). Report the legacy-Turbo capability to Handy as a follow-up to [#1746](https://github.com/cjpais/Handy/issues/1746). **Upstream candidate** (the report).

### History: keep more, store less

**Problem:** inherited from Handy, the history keeps a fixed number of entries (default 5, `history_limit`) together with their recordings. Recordings are uncompressed WAV (16 kHz mono 16-bit, about 1.9 MB per minute), which is why the limit is small; the transcripts themselves take almost no space.

**Done:**

- Recordings are stored as **Ogg Opus** at 24 kbit/s, about 12 times smaller than WAV (9 MB per hour of dictation); in a test with real dictations, re-transcribing them gave the same text as the WAV originals. Existing WAV recordings are converted once at startup.
- A **storage limit** (100 MB, 500 MB by default, 1 GB, 5 GB or unlimited) replaces the count and age options; over it, the oldest recordings are deleted. Saved entries and transcribed files count but are never deleted automatically, and the newest recording is always kept.
- **Transcripts stay** when their recording is deleted; the entry says the recording was removed.
- The history player and "Re-transcribe" decode recordings in the backend, so playback does not depend on the webview's codecs.

**Upstream candidate.**

There each is the key equivalent of a service of its own ("End Dictation and Insert", and "End Dictation with Post-processing and Insert" for the post-process shortcut), which ends the recording and answers once the text is ready, as the first idea does. The context shortcut got a third one on 2026-11-13, "End Dictation with Context and Insert"; like a press of its shortcut, a service adds post-processing or context to the recording it ends but never takes them away (shortcut and service gone again on 2026-11-15, see "Context by a switch instead of its own shortcut"). DanyWhere keeps the services' shortcuts equal to the dictation shortcuts and takes the shortcuts back as soon as the recording ends, for whatever reason. A setting under General ("Dictation shortcut also inserts", on by default without Accessibility) switches it off. The ⌘-or-⌃ rule of "Insert Last Dictation" turned out to hold for the services too: on the company Mac (2026-11-13) ⌥Space and ⌥⇧Space never reached their services, ⌃ did, since ⌥ with a character key types a character. A dictation shortcut with ⌥ or ⇧ alone therefore gets no service shortcut and is not released, so its second press ends the dictation the way it does with "Insert Last Dictation"; function keys need neither. The macOS defaults use ⌃ instead of ⌥ since then (user, 2026-11-13: ⌃Space, ⌃⇧Space, ⌃⇧⌘Space for context, ⌃⇧V, ⌃⇧L). Both ship with 0.1.6. **Tried by hand on 2026-11-12** in NoAX: ⌃⇧Space works as a service key equivalent; the plain shortcut ended and inserted two dictations, the post-process shortcut three. Limits:
  - **Push-to-talk** stays as before: a key release reaches no app, so the text waits for "Insert Last Dictation".
  - **Where no service can take the press** (the Finder, no text field), the second press does nothing and the recording keeps running. There, "Paste Last Transcript" ended the recording and put the text on the clipboard once it was ready (tried in NoAX on 2026-11-14), since 2026-11-14 "Copy Last Transcript" (⌃⇧C); Escape cancels.
  - **Apps that are already open** learn the services' shortcuts only after a restart, as with "Insert Last Dictation" (the user's iTerm2 on the company Mac, 2026-11-13). **Done** (the user's choice, 2026-11-13; ships with 0.1.6): DanyWhere keeps the time it last wrote the services' shortcuts; while a locked recording runs and the app in front was launched before that, it keeps its shortcuts, so the second press ends the dictation through DanyWhere, the text goes on the clipboard and a notice names the app to restart. It looks again whenever another app comes to the front. Settings from 0.1.5 take the time the services settings file last changed.
  - **When nothing records** (DanyWhere wasn't running and macOS started it to answer the service, or its global shortcut failed to register), these services never insert an earlier dictation (user, 2026-11-12). A setting next to the first one chooses: start a recording for that shortcut, locked, so its next press ends and inserts it (the default; the user found it "noch besser"), or do nothing. The call is answered with nothing at once; the recording starts as soon as DanyWhere is ready, or not at all after 15 s.
- **An input method of DanyWhere's own** (set aside on 2026-11-11 as more work): an input method can insert text at any moment, with no key press at all. Input methods also work in Apple's Terminal; whether an insertion without a key press works there is untested. The user has to add it once as an input source and keep it selected. Whether a managed Mac allows a third-party input method is unknown; a minimal test input method on the company Mac would tell.

**Paste with ⌃⇧V, copy with ⌃⇧C, with Accessibility and without** (user, 2026-11-14): without Accessibility "Paste Last Transcript" (⌃⇧V) put the last dictation on the clipboard, over what the user had copied, while ⌃⌥⌘V inserted it; with Accessibility ⌃⇧V pastes. The user found that the same key did something else in the two states, and that ⌃⇧V overwrote the clipboard "die fast schlechteste Lösung". Now:

- **⌃⇧V inserts in both states.** Without Accessibility it is the shortcut of "Insert Last Dictation" instead of ⌃⌥⌘V, and DanyWhere doesn't register it, so the press reaches the app in front: the service inserts the last dictation there, or ends a running one and inserts it once it's ready. The field "Paste Last Transcript" under General changes it; the separate field of the service is gone. Without Accessibility it refuses a combination a service can't have (one without ⌘ or ⌃, or one another DanyWhere shortcut uses). A stored combination a service can't have (⌥⇧V, the macOS default up to 0.1.5) stays DanyWhere's and copies as before, and the service keeps ⌃⌥⌘V; existing installations keep their combinations, as with the ⌃ defaults of 0.1.6.
- **⌃⇧C "Copy Last Transcript"** (Alt+Shift+C on Windows and Linux) puts the last dictation on the clipboard, in both states. During a dictation it ends it and puts the text on the clipboard once it's ready, instead of pasting it or keeping it for the service: the way out where no service takes the press (the Finder, no text field).
- Apps that are already open learn the service's new shortcut only after a restart; until then ⌃⇧V does nothing there, ⌃⇧C works.

Next steps:

- **Switch automatically.** Today the user chooses the mode once in onboarding and it stays, even if the permission is granted later. Instead: without the permission, use the mode without Accessibility with a short notice; once the permission is granted, return to the full mode on its own.
- **Test both states through one permission check.** Route every Accessibility check (backend and frontend) through a single function that tests can replace, and cover the whole flow — onboarding, startup, shortcut backend, input simulation, paste vs. clipboard — once with "granted" and once with "not granted". Component tests for the onboarding need a React test setup, which the project does not have yet. A real run without the permission stays necessary when code around permissions, pasting or shortcuts changes, because the operating system and third-party libraries can behave in ways a mock does not show.
