# DanyWhere roadmap

Planned work on DanyWhere, roughly in priority order within each section. Items that would benefit every Handy user are marked **upstream candidate** and are offered to [Handy](https://github.com/cjpais/Handy) as well.

## Features and improvements

### Transcription in the cloud, post-processing on this Mac

**Idea (user, 2026-11-17; partly decided, see below):** transcription is local only, post-processing in practice cloud only. Both should work either way: transcription by a subscribed cloud service, which might be faster thanks to the providers' hardware, and post-processing by a language model installed on this Mac.

**Found (2026-11-17):**

- Transcription is already fast: Canary 1B v2 decodes during the recording, so the text is there about 1 s after the key is released (median 1.1 s over 13 dictations of up to 134 s). Uploading the recording to a cloud service takes about as long; only streaming services (about 0.3 s) would be faster. A cloud service could still hear better: German, German mixed with English, and names from the word lists given as vocabulary. Costs would be 1–5 USD a month. Handy declines cloud transcription on principle ("local-only"), so this would be DanyWhere's own.
- The wait is in post-processing (median 7 s, up to 20 s, with Claude Haiku 5.5 at effort `xhigh`).
- Post-processing on this Mac works today without code changes: the "Custom" provider points at Ollama, needs no key and asks the model not to think. Measured with the user's prompt on an M1 Pro with 16 GB: of Qwen 3.5 4B and 9B, Ministral 3 8B and Gemma 4 12B, only Gemma 4 12B followed the prompt well enough, at about 3 s for short and 18–27 s for long dictations, a 31 s cold start and about 8 GB of memory. The smaller ones left dictation commands in, kept misheard names or wrote text of their own into the result. Local post-processing is therefore a matter of privacy, not speed. Ollama loads models with a 4096-token context, which the frame and a long prompt nearly fill.
- Apple Intelligence is listed but has never worked in a release: the macOS releases are built with the Command Line Tools only, which compile the provider as a stub.
- Apple's on-device model itself (FoundationModels, macOS 26) was measured the way DanyWhere asks it without guided generation, with a small tool that builds with the Command Line Tools: it took the long prompt without a context error but hardly followed it. Dictation commands and misheard names stayed, the transcript often came back with its tags, and once it translated the English sentence into German. Unusable for this prompt; whether guided generation (`@Generable`, which needs full Xcode) does better is untested.

**Decided (2026-11-17; the user's answers, the rest decided by Claude on the user's behalf):**

- Compare OpenAI's transcription models with the local ones on 20–30 real recordings from the History (the user allowed real recordings to leave the Mac for this); OpenAI only, since no other key is at hand.
- No cloud transcription in 0.2.2. If the comparison shows clearly fewer mishearings, a branch builds it for the user to look at first.
- Apple Intelligence is not repaired for now (finding above).
- A small part of the local providers comes first: the warm-up and the mark (below). The switch "Only on this Mac", dedicated Ollama and LM Studio providers, the context size and the History recording where each step ran stay for later, with the user.
- The company Mac is an M4 Pro with 24 GB: Gemma 4 12B fits there, and Gemma 4 26B-A4B (a mixture of experts, about 16 GB) is worth a try there.

**Measured (2026-11-18):** OpenAI's transcription against DanyWhere's stored local text, on 28 real dictations (17 min, Canary 1B v2 and Whisper large-v3-turbo) and, for the names and words the user's prompt corrects, 38 older ones; five OpenAI runs, 0.65 USD in all. `gpt-transcribe` hears general text slightly better: of 55 places where it and the local model write differently, it was right at 12 and the local model at 3, about 0.7 % against 0.2 % of the words, half of them English technical terms and program names in German speech; post-processing fixes 5 of those 12. On the corrected names and words it is no better with the same word list (31 of 55 spelled right against 44 locally) and only slightly better with the names added as keywords (45). For short dictations it is as fast as the local model after the key is released (median 0.9 s against 1.15 s), from 30 s on slower (1.8 s) as long as the whole file is uploaded after the recording. **No clear gain, so cloud transcription is not built without the user.** Claude's idea, not measured: add the two first names and "Beistrich" to the word list first.

**Done (2026-11-18, ships with 0.2.2):** when a recording starts for a dictation that post-processes with a provider on this computer (its address is `localhost` or a loopback address), DanyWhere asks the model for a one-token answer, so a local server such as Ollama or LM Studio loads it while the user speaks instead of after the recording. The request runs on its own, one at a time, never holds up the recording, and its errors only go to the log. Next to the post-processing provider, the settings say "On this Mac" (elsewhere "On this computer") or "Cloud", by the same rule.

**Claude's ideas (not decided):** a cloud transcription provider per profile speaking OpenAI's `/v1/audio/transcriptions`, uploading the chunks during the recording and falling back to the local model; dedicated "Ollama" and "LM Studio" providers that load the model when the recording starts and send the context size; every provider marked "On this Mac" or "Cloud" by its address, the History recording where each step ran, and a switch "Only on this Mac" for the company Mac; macOS releases built with Xcode so Apple Intelligence works.

### Tray menu and main window: DanyWhere as a normal application

**Idea (user, 2026-11-16; next after 0.2.0):** the History is not a setting, yet the tray menu reaches it only through "Settings...". It should get a menu item of its own, or the window should open on the History and offer a button to the settings there. The tray's "Copy Last Transcript" can go, since the shortcut (⌃⇧C, Alt+Shift+C elsewhere) does the same.

**Idea (user, 2026-11-16, later; noted for later, not to be started yet):** this is a larger topic than the tray menu. The main window, which would then hold the History, should behave like a normal application rather than a tray utility that only has settings, and the settings would be opened from within that application.

**Claude's ideas (not decided):**

- The window opens on the History as its home. The settings move out of the History's sidebar into a place of their own: on macOS a separate Settings window behind ⌘, and "DanyWhere → Settings…", as Mac applications do; on Windows and Linux the same window, or a section reached from the window's foot.
- A real menu bar on macOS: DanyWhere (About, Settings…, Check for Updates, Quit), Edit (editing History texts needs it anyway), View (e.g. search with ⌘F), Window and Help. Windows and Linux get the same commands in the window and the tray.
- The Dock icon: today it appears only while the window is open and goes away when the window is closed (activation policy `Accessory`). A setting "Show in Dock" (always / only while the window is open) would let DanyWhere be reached with ⌘Tab like any application; the tray stays for status and quick actions.
- What closing the window and ⌘Q do, to be decided with this: today closing only hides the window and DanyWhere stays in the tray. Dictation keeps working in the background either way.
- The tray menu shrinks to status, profile, "Open DanyWhere" (the History), "Settings…", updates and quit; "Copy Last Transcript" goes.
- The window keeps its size, position and the page last open.

### Profiles per application: decide where the text goes, not where the recording starts

**Idea (user, 2026-11-16):** the application in front when the dictation shortcut is pressed picks the profile today. It should be the application the text goes into: a dictation started in a window without a text field (e.g. the Finder) waits for "Paste Last Transcript" and is inserted elsewhere later, with the wrong profile's transcription, post-processing and "Append" text. Decided (user, 2026-11-16, following Claude's proposal): decide at the end of the recording, which without Accessibility is exactly the app that calls the service, and check again on inserting; if the target's profile differs then, redo from the first step whose settings differ (transcription from the kept recording, post-processing, or only the appended text); the window for the context is captured at the end of the recording too.

**Done (2026-11-16, ships with 0.2.1):** the profile is chosen again when the recording ends, by the application in front then; the start's profile still has its model preloaded, and when the end's profile transcribes differently (model, languages, word list in use, filler words) the recording is transcribed in one go with its model, a live transcription included. Before a dictation goes into an application (pasted with Accessibility, inserted by the service call it made, or later with "Paste Last Transcript" or "Insert Last Dictation"), DanyWhere looks at that application's profile and redoes the dictation from the first step that differs: transcribing the kept recording again, post-processing the transcription again, or neither; the target's "Append" text applies in any case. History records a redo as "Transcribe Again" and the post-processing from History do; an entry the user changed there is not redone, only the target's "Append" text applies (confirmed by the user, 2026-11-16: the user's text wins). The window for the context is captured at the end of the recording. "Copy Last Transcript" keeps the dictation's profile. Only the last dictation's profile is known, and only until DanyWhere quits.

### Overlay on the screen of the focused window

**Idea (user, 2026-11-16):** the overlay should show on the screen with the focused window, whether or not text can be inserted there. Today it takes the screen with the mouse pointer, read through Enigo, which exists only with Accessibility, so without it the overlay always shows on the main screen. Claude's proposal: the screen holding most of the front application's top window (macOS: `NSWorkspace` plus `CGWindowListCopyWindowInfo`, which give the window's bounds without Accessibility), else the pointer (`CGEventGetLocation`, also without Accessibility), else the main screen; decided on each overlay state change. Decided as proposed (user, 2026-11-16). **Upstream candidate** (Handy has the same fallback without Enigo).

**Done (2026-11-16, ships with 0.2.1):** as proposed for macOS. On Windows the overlay takes the monitor the foreground window is on (`MonitorFromWindow`) and the pointer from `GetCursorPos`; on Linux it still takes the pointer from Enigo. On a tie the screen with the pointer wins.

**Follow-up (user, 2026-11-17):** the overlay keeps the screen it took when its state last changed: switching to a window on another screen during the recording or the transcription leaves it behind. It should follow the screen of the focused window for as long as it shows a dictation, and the profile it names should follow the application in front the same way (the profile is chosen again when the recording ends and checked again on inserting, see "Profiles per application: decide where the text goes, not where the recording starts").

### Window titles without Accessibility: find the apps instead of a fixed list

**Idea (user, 2026-11-13):** the company Mac has Edge, not Chrome. Instead of a fixed list (iTerm2, Terminal, Chrome, Safari, the classic Outlook), find out which applications can tell their window title. Claude's finding: an app's `Info.plist` and scripting definition (`.sdef`, with the standard suite it includes) tell, without sending it an Apple event, whether and how to ask it: Chromium browsers (`active tab`, and `mode` for incognito windows), Safari-like browsers (`current tab`), iTerm2 (a rule of its own), and every app whose dictionary has the standard suite's window name. Decided (user, 2026-11-17, following Claude's recommendations): the settings list at least every running app that can tell a title, more where useful; an app without a rule of its own gets the name of its front window; private windows of browsers that don't mark them (Safari) are read as with Accessibility, Chromium's incognito windows stay out. Every app still needs the user's "Allow …".

**Brought forward (user, 2026-11-18):** on the company Mac, 0.2.2 without Accessibility put iTerm2's window title into the History, but not TextEdit's: TextEdit was not on the fixed list. So this ships on its own, ahead of the other overlay and second-press work.

**Done (2026-11-17, ships with 0.2.3):** the fixed list is gone (`src-tauri/src/title_query.rs`). An app's bundle decides how to ask it, read from its files only: the `Info.plist` names the scripting definition (also without its `.sdef` extension, as Messages does; "dynamic" counts as none), whose classes are read with their class extensions, inherited classes (Music's and TV's window takes its name from `item`) and included files (`file://localhost/…`, `file:///…` or relative, macOS's standard suite among them). A window with `active tab` whose tab has a `title` is asked like Chromium, and a window that isn't "normal" answers nothing when the window has `mode` (incognito, InPrivate); `current tab` with a tab `name` is asked like Safari; any other window with a `name` gives the front window's name; iTerm2 keeps its own rule. An app with only `NSAppleScriptEnabled` gives the front window's name when it ships an old Cocoa `.scriptSuite` (TextEdit, Automator, Script Editor, System Information: their suites build on Foundation's standard suite, which has the window's name), and nothing without any scripting file (Chrome's web-app wrappers, OneDrive, Preview). The answer is kept per bundle until its `Info.plist` changes, and is read ahead in the background at start, so a dictation normally finds it in the cache. Only bundle ids made of letters, digits, dots and hyphens go into the AppleScript. The settings list the running apps that can tell a title, with their status and "Allow …", and below them, under "Installed, not running", the installed ones (macOS can only ask about a running app); DanyWhere itself is left out, and the list is read again when the window gets the focus back. On this Mac 28 of 116 installed apps can tell a title. An app on the excluded list is not asked at all; before, it was asked and its answer dropped. Not yet seen in the app: Edge (only on the company Mac).

**Checked without Accessibility, and fixed (2026-11-18, ships with 0.2.4):** in DanyWhere NoAX, TextEdit was listed and could be allowed, but the first dictation right after allowing it got no window: TextEdit took longer than the 700 ms a capture gives the Apple event. Four dictations after that got its title in about 250 ms each. Now an app that hasn't answered yet is asked once in the background when the recording starts (limit 5 s), while the user speaks; apps that have answered are remembered by bundle id and process id and not asked ahead again. Checked with Chrome just allowed and never asked: the question ahead took 446 ms, the capture at the end 277 ms with the title; the second dictation asked nothing ahead.

### History: drop the pencil

**Idea (user, 2026-11-16; for one of the next steps):** the pencil next to an entry is superfluous now: a click into the text already opens it for editing. The wand (post-processing) stays.

**To check first (Claude):** whether the text box can be reached and opened for editing from the keyboard (Tab, then Enter or Space) without the pencil; if not, the box needs that before the pencil goes. Now Tab reaches the box while it can be edited and shows a focus ring; plain Enter or Space edits it with the caret at the end (not with a modifier, a held key or during IME input). When a key ends the edit (Escape, ⌘↩, Enter on Save or Cancel), the focus goes back to the box, so the keyboard goes on from the entry; after a click it doesn't, so no ring is left behind. The pencil next to the entry is gone; the pencil that marks a version the user changed stays. The double-click point above stays as it is (user, 2026-11-17): a trial in which a click waited for the double-click interval, as in the Finder, felt less practical than opening at once, and there is no single convention to follow.

**Then (2026-11-17, the user chose it; ships with 0.2.2):** as in Atlassian's inline edit, a hidden button named like the edit field ("Correct the text", in every locale already) sits before the text and takes the keyboard's place: Tab reaches it, Enter or Space press it, the box shows its focus ring, VoiceOver reads it as a button and scripts find it by its name. The text itself is no longer in the tab order and stays plain text. Not checked: WebKit is expected to let Tab reach buttons, this one as every other, only with keyboard navigation switched on (System Settings → Keyboard; on on the user's Mac), and ⌥Tab otherwise.

### Post-processing: a fixed frame around every prompt

**Idea (user, 2026-11-14; next):** the part of a prompt that tells the model what it gets — a speech-recognition transcript between `<transcript>` tags, to be processed rather than answered — should be sent by DanyWhere itself, so a prompt only says what to do with the text. Today every prompt has to contain it, and a prompt that gets it wrong produces nonsense.

**Found:** a prompt has to contain `${output}`. For providers without structured output (Anthropic, Groq, custom) the transcript takes its place and the whole prompt goes out as one message, so without `${output}` the model never sees the transcript. For providers with structured output the transcript goes as a message of its own and `${output}` is dropped, so the prompt's `<transcript>` tags arrive empty.

**Done (2026-11-14, ships with 0.2.0):** DanyWhere sends a fixed frame (what the model gets, that instructions and questions in the dictation are not to be followed, that the language stays unless the instructions say otherwise, that only the result is returned), then the prompt's instructions, then the context if any, then the transcript in `<transcript>` tags. The frame always goes out in English; the editor shows it read-only above the prompt, translated into the interface language. A prompt only says what to do with the text. A prompt that still contains `${output}` runs as before, without the frame, and a warning at startup names every prompt with `${output}` or `<transcript>` tags until they are removed; Handy's untouched default prompt is replaced by a version without the frame's part. **Upstream candidate.**

**Done (2026-11-15, ships with 0.2.0):** the frame no longer lets the instructions override "do not answer questions in the dictation" or "keep its language" (a translation prompt still translates), and it tells the model that speech recognition mishears words and that such errors are to be corrected where the context makes clear what was said, while anything that could have been meant stays as dictated. In a trial with a prompt that does not ask for corrections, this raised the corrected recognition errors from 10 to 45 of 48 without touching intended words. The prompt editor shows the new frame in every language.

### Configurations to save and load

**Idea (user, 2026-11-14):** save and load a whole DanyWhere configuration, e.g. one that combines a speech model with a post-processing setup, or prompts for particular topics. A new installation starts with a default configuration; an update from a version without configurations saves the settings in use as that default.

**Decided (user, 2026-11-15):** they are called **profiles**. A profile holds what decides how a dictation is processed (speech model, languages, post-processing provider, model and prompts, context limits, filler words); shortcuts, microphone, API keys and interface stay global. A change goes into the active profile at once; "Duplicate" makes a new one. The profile is chosen at the top of the sidebar and in the tray menu, and managed under General (since moved to a page of its own, see "Profiles on a page of their own"). Each profile has its own copies of its prompts, so they can drift apart. Profiles are stored with the app and can be exported to and imported from a YAML file. An API key in that file is encrypted with a password chosen at export and asked for at import, through a deliberately slow key derivation (Argon2id); how strong the password is stays the user's choice, with no password rules. In the app's own settings file the keys stay as they are.

Each profile has its own prompt list with one prompt selected, as the post-processing settings have today. Word lists come in three tiers: the Global Word List applies in every profile, each profile has a list of its own that always applies in it, and each profile has its own additional lists, of which at most one is switched on, as today. An exported profile always carries its provider's API key, encrypted; importing without the key is always possible.

**Done (2026-11-15, ships with 0.2.0):** all of the above, checked in real runs. The first start of the new version turns the settings in use into the default profile.

### Profiles per application

**Idea (user, 2026-11-15):** associate applications with profiles, so that dictating into a given application uses its profile.

**Done (2026-11-15, ships with 0.2.0):** each profile lists the applications it is used for, and an application belongs to at most one profile. The frontmost application at the start of a dictation picks the profile for that dictation, speech model included; the profile chosen in the sidebar stays as it is and applies to every other application. A "choose the profile by application" switch in the tray, the sidebar and the profile settings, also toggled by a shortcut (⌃⇧A on macOS, Alt+Shift+A elsewhere) that reports the new state, gets past an association without editing it; while it is off and an association exists, the tray icon shows a padlock. macOS lists the applications to choose from; on Windows their executable names are typed in; Linux has no frontmost application yet.

**Done (2026-11-15, ships with 0.2.0):** the overlay shows the state of "choose the profile by application" by a glyph alone (a window when on, a padlock when off, none without an association) and the profile by its name: when the shortcut toggles it, when the profile changes, and, with two or more profiles, during every dictation. Each such pill is as wide as its content; a fixed width used to cut off "on" and "off" alike. The compact overlay window is 320px wide instead of 266, so the working pill keeps room for the name.

### Word lists behave differently per speech model

**Found (2026-11-12, to be discussed):** models that take a vocabulary, such as Whisper, get the word lists as one and skip the replacement afterwards. Models without, such as Parakeet, get a fuzzy replacement of similar words after the transcription, which turned every "Bild" into "Build" once "Build" was in a list. The same list therefore helps with one model and harms with another.

### Post-processing: known terms from the word lists

**Idea (2026-11-15, the user agreed: "words or phrases"):** send the entries of the word lists in effect, words or phrases such as "DanyWhere Dev" or "Pull Request", to the post-processing model as known terms. It could then turn a misheard "Danny Ware" into "DanyWhere" and tell "Bild" from "Build" by the context, which the speech recognition cannot do with a vocabulary alone.

### Post-processing: choose the effort next to the model

**Idea (user, 2026-11-15):** choose the effort (how much the model thinks) next to the post-processing model, per profile. In a trial, Claude Sonnet 5.5 sometimes wrote its own correction into the result ("Wait — I must not add words. Corrected output:" and the text a second time), because it does not think on short dictations at its default effort; at effort `xhigh` it never did. Claude Haiku 5.5 hardly ever slips this way, but at its default it often smooths the grammar silently against a prompt that asks to keep the text unchanged; `high` reduces that at about 2 s more per dictation. Anthropic's Models API reports for every model which effort levels it accepts (`capabilities.effort`; none for Claude Haiku 4.5 and Sonnet 4.5, no `xhigh` for the 4.6 models), so the choice can offer exactly those, with the model's default as the first entry; other providers keep their behavior for now.

**Done (2026-11-15, ships with 0.2.0):** a choice "Effort" under the post-processing model, stored per profile and provider (exported and imported with the profile), for every provider except Apple Intelligence. "Model Default" sends what was sent before. The levels come from the model list where it names them (Anthropic `capabilities.effort`, OpenRouter `reasoning.supported_efforts`, DeepSeek `effort.supported_levels`), else from what the provider documents per model family (OpenAI gpt-5.x and o-series, Groq, Cerebras, Z.AI, DeepSeek), else low/medium/high. Anthropic gets `output_config.effort`, adaptive thinking where the model thinks only on request, and `max_tokens` 16000; OpenRouter `reasoning.effort`; everyone else `reasoning_effort`. An endpoint that refuses the level gets the request again without it, the refusal is remembered while the app runs, and the dictation shows the warning "Effort Not Accepted".

### A sound when everything is done

**Idea (user, 2026-11-15):** besides the start and stop sounds, a third one once a dictation is completely done, post-processing included: right after the stop sound without post-processing, after the post-processing with it, which at a high effort often takes long enough for the user to look elsewhere. It makes no difference whether the text was pasted or only put on the clipboard. The sound is the high E (marimba on E5) that so far said a dictation waits on the clipboard.

**Done (2026-11-15, ships with 0.2.0):** every dictation whose text was delivered ends with that sound: pasted, inserted by the service, left on the clipboard, ready for the service, or only kept in the History; also when the post-processing failed and the raw transcript was pasted. It replaces the waiting sound after dictations, so no dictation plays two; the overlay still says where the text waits. No sound when nothing came out, pasting failed, after Escape, or once a newer dictation has started. A switch "Sound When Done" under Sound, on by default, works while Audio Feedback is on; switched off, the waiting sound plays as before. A custom theme may add `custom_done.wav` and otherwise uses its clipboard sound. "Paste Last Transcript", "Copy Last Transcript" outside a dictation and post-processing in the History play no done sound. The log line "Dictation done; playing the done sound." shows when DanyWhere tried to play it.

### Context by a switch instead of its own shortcut

**Idea (user, 2026-11-15):** a switch "send context", toggled like "choose the profile by application" (tray, sidebar, a shortcut), decides whether a dictation with post-processing sends earlier dictations as context; without post-processing never. Per application it follows the profile if the switch is a profile value. Open: whether the Context Hotkey goes, whether the switch is global or per profile, and how the overlay shows it.

**Done (2026-11-15, ships with 0.2.0):** the switch "Send Context" belongs to the profile and is off by default. While it is on, a dictation with post-processing sends the earlier dictations of the same window as context, with the same limits as before; without post-processing it never does. ### Space between consecutive dictations

**Problem:** dictating into the same text field in several separate recordings (record, stop, record again) glues the pieces together: "…end of sentence.Next sentence…".

**Cause (inherited from Handy):** every recording is pasted on its own, with nothing before it and — unless the off-by-default setting "append trailing space" (`append_trailing_space`) is on — nothing after it. Within a single long recording there is no problem: the chunks of long-form transcription are joined with spaces (`join_transcripts` in `src-tauri/src/audio_toolkit/chunking.rs`, covered by tests; verified with a 60 s recording).

**Options:**

1. Turn on the existing trailing-space setting by default. Simple, but leaves a trailing space at the end of a field and before punctuation typed afterwards.
2. Look at the character before the cursor (macOS Accessibility: focused element's selected text range and the text before it) and prepend a space only when it is a letter, digit or sentence punctuation. Exact, but needs the Accessibility permission and is not supported by every app; fall back to option 3 or 1.
3. Remember the last paste (target app, time, last character) and prepend a space when the next dictation goes into the same app shortly afterwards and the previous one did not end in whitespace. Works without Accessibility; can be wrong if the cursor was moved in between.

**Proposal:** option 2 where available, option 3 as fallback (e.g. in "continue without Accessibility" mode); never add a space before text that starts with punctuation, and respect languages without word spacing (reuse `is_unspaced` from the chunk joiner). **Upstream candidate.**

**Deferred:** not before the first public release; the preferred behaviour is still open.

### Named word lists

**Problem:** there is one list of custom words for everything. Whisper models get the list as a short context ("Glossary: …") of at most 223 tokens (roughly 70–100 German words); what does not fit is dropped from the end. Parakeet and Canary have no such input; for them DanyWhere replaces similar-sounding words after transcription, and only for entries without umlauts or ß. One long list mixing topics therefore biases recognition less precisely than a short list for the topic at hand.

**Done:** the custom words are now the **Global Word List**, which always applies. Named additional lists (e.g. "Work", "Programming") are managed in the Advanced settings the same way as the post-processing prompts; one of them or none is switched on in addition. The model gets the additional list's words first, then the global ones. The shortcut ⌥⇧L steps through the lists (only global → first list → … → only global) and shows the result briefly in the overlay; the tray menu shows the active list and switches it.

### Phantom phrases at the end of a recording

Whisper sometimes appends text that was never said when the recording ends in silence (observed: "Vielen Dank." after a synthetic 60 s German recording). Known Whisper behaviour on trailing silence. To check: whether trimming trailing silence with the VAD before decoding (or dropping a final chunk without speech) avoids it.

### Translation to English

**Problem:** Whisper large-v3-turbo, DanyWhere's default model, cannot translate (it was fine-tuned on transcription data only). The legacy `ggml-large-v3-turbo.bin` still reports translation support, so "Translate to English" is offered, the log says "(translated)", and the text stays in the spoken language (reproduced 2026-10-24). DanyWhere lets the catalog's capabilities win (the GGUF Turbo is marked `translate: false`), so the option no longer appears for Turbo (verified 2026-10-26).

**Options:** translate with Whisper medium or small (trained for translation; both in DanyWhere's selection), or with LLM post-processing (a "translate to English" prompt; usually better quality, needs a provider). Report the legacy-Turbo capability to Handy as a follow-up to [#1746](https://github.com/cjpais/Handy/issues/1746). **Upstream candidate** (the report).

### History: keep more, store less

**Problem:** inherited from Handy, the history keeps a fixed number of entries (default 5, `history_limit`) together with their recordings. Recordings are uncompressed WAV (16 kHz mono 16-bit, about 1.9 MB per minute), which is why the limit is small; the transcripts themselves take almost no space.

**Done:**

- Recordings are stored as **Ogg Opus** at 24 kbit/s, about 12 times smaller than WAV (9 MB per hour of dictation); in a test with real dictations, re-transcribing them gave the same text as the WAV originals. Existing WAV recordings are converted once at startup.
- A **storage limit** (100 MB, 500 MB by default, 1 GB, 5 GB or unlimited) replaces the count and age options; over it, the oldest recordings are deleted. Saved entries and transcribed files count but are never deleted automatically, and the newest recording is always kept.
- **Transcripts stay** when their recording is deleted; the entry says the recording was removed.
- The history player and "Re-transcribe" decode recordings in the backend, so playback does not depend on the webview's codecs.

**Upstream candidate.**

The real wish is to insert as with Accessibility: the second press of the dictation shortcut ends the dictation, and the text appears once it is ready. Ideas (Claude's); the user chose the first one (2026-11-12):

- **The insert shortcut also ends a dictation.** **Done** (ships with 0.1.5): pressed while recording, the service stops the recording; pressed while transcribing, it waits. It answers once the text is ready, instead of inserting nothing; then neither the waiting sound nor the "Ready" notice comes. The app being typed in waits meanwhile, up to the service's `NSTimeout` of 30 s; DanyWhere gives up after 20 s, and the dictation then waits for the shortcut as before. One shortcut starts a dictation, the other ends and inserts it, with no waiting for the sound. It works in the same apps as before. DanyWhere answers the service on its main thread and keeps that thread's run loop going while it waits.
- **One shortcut for both.** **Done** (user's choice, 2026-11-12; ships with 0.1.5): while a recording runs that only the next press ends (toggle, or hold-or-toggle after a tap), DanyWhere releases both dictation shortcuts, so their second press reaches the app being typed in. There each is the key equivalent of a service of its own ("End Dictation and Insert", and "End Dictation with Post-processing and Insert" for the post-process shortcut), which ends the recording and answers once the text is ready, as the first idea does. The context shortcut got a third one on 2026-11-13, "End Dictation with Context and Insert"; like a press of its shortcut, a service adds post-processing or context to the recording it ends but never takes them away (shortcut and service gone again on 2026-11-15, see "Context by a switch instead of its own shortcut"). DanyWhere keeps the services' shortcuts equal to the dictation shortcuts and takes the shortcuts back as soon as the recording ends, for whatever reason. A setting under General ("Dictation shortcut also inserts", on by default without Accessibility) switches it off. The ⌘-or-⌃ rule of "Insert Last Dictation" turned out to hold for the services too: on the company Mac (2026-11-13) ⌥Space and ⌥⇧Space never reached their services, ⌃ did, since ⌥ with a character key types a character. A dictation shortcut with ⌥ or ⇧ alone therefore gets no service shortcut and is not released, so its second press ends the dictation the way it does with "Insert Last Dictation"; function keys need neither. The macOS defaults use ⌃ instead of ⌥ since then (user, 2026-11-13: ⌃Space, ⌃⇧Space, ⌃⇧⌘Space for context, ⌃⇧V, ⌃⇧L). Both ship with 0.1.6. **Tried by hand on 2026-11-12** in NoAX: ⌃⇧Space works as a service key equivalent; the plain shortcut ended and inserted two dictations, the post-process shortcut three. Limits:
  - **Push-to-talk** stays as before: a key release reaches no app, so the text waits for "Insert Last Dictation".
  - **Where no service can take the press** (the Finder, no text field), the second press does nothing and the recording keeps running. There, "Paste Last Transcript" ended the recording and put the text on the clipboard once it was ready (tried in NoAX on 2026-11-14), since 2026-11-14 "Copy Last Transcript" (⌃⇧C); Escape cancels.
  - **Apps that are already open** learn the services' shortcuts only after a restart, as with "Insert Last Dictation" (the user's iTerm2 on the company Mac, 2026-11-13). **Done** (the user's choice, 2026-11-13; ships with 0.1.6): DanyWhere keeps the time it last wrote the services' shortcuts; while a locked recording runs and the app in front was launched before that, it keeps its shortcuts, so the second press ends the dictation through DanyWhere, the text goes on the clipboard and a notice names the app to restart. It looks again whenever another app comes to the front. Settings from 0.1.5 take the time the services settings file last changed.
  - **When nothing records** (DanyWhere wasn't running and macOS started it to answer the service, or its global shortcut failed to register), these services never insert an earlier dictation (user, 2026-11-12). A setting next to the first one chooses: start a recording for that shortcut, locked, so its next press ends and inserts it (the default; the user found it "noch besser"), or do nothing. The call is answered with nothing at once; the recording starts as soon as DanyWhere is ready, or not at all after 15 s.
- **An input method of DanyWhere's own** (set aside on 2026-11-11 as more work): an input method can insert text at any moment, with no key press at all. Input methods also work in Apple's Terminal; whether an insertion without a key press works there is untested. The user has to add it once as an input source and keep it selected. Whether a managed Mac allows a third-party input method is unknown; a minimal test input method on the company Mac would tell.

**Paste with ⌃⇧V, copy with ⌃⇧C, with Accessibility and without** (user, 2026-11-14): without Accessibility "Paste Last Transcript" (⌃⇧V) put the last dictation on the clipboard, over what the user had copied, while ⌃⌥⌘V inserted it; with Accessibility ⌃⇧V pastes. The user found that the same key did something else in the two states, and that ⌃⇧V overwrote the clipboard "die fast schlechteste Lösung". Now:

- **⌃⇧V inserts in both states.** Without Accessibility it is the shortcut of "Insert Last Dictation" instead of ⌃⌥⌘V, and DanyWhere doesn't register it, so the press reaches the app in front: the service inserts the last dictation there, or ends a running one and inserts it once it's ready. The field "Paste Last Transcript" under General changes it; the separate field of the service is gone. Without Accessibility it refuses a combination a service can't have (one without ⌘ or ⌃, or one another DanyWhere shortcut uses). A stored combination a service can't have (⌥⇧V, the macOS default up to 0.1.5) stays DanyWhere's and copies as before, and the service keeps ⌃⌥⌘V; existing installations keep their combinations, as with the ⌃ defaults of 0.1.6.
- **⌃⇧C "Copy Last Transcript"** (Alt+Shift+C on Windows and Linux) puts the last dictation on the clipboard, in both states. During a dictation it ends it and puts the text on the clipboard once it's ready, instead of pasting it or keeping it for the service: the way out where no service takes the press (the Finder, no text field).
- Apps that are already open learn the service's new shortcut only after a restart; until then ⌃⇧V does nothing there, ⌃⇧C works.

Next steps:

- **Switch automatically.** Today the user chooses the mode once in onboarding and it stays, even if the permission is granted later. Instead: without the permission, use the mode without Accessibility with a short notice; once the permission is granted, return to the full mode on its own.
- **Test both states through one permission check.** Route every Accessibility check (backend and frontend) through a single function that tests can replace, and cover the whole flow — onboarding, startup, shortcut backend, input simulation, paste vs. clipboard — once with "granted" and once with "not granted". Component tests for the onboarding need a React test setup, which the project does not have yet. A real run without the permission stays necessary when code around permissions, pasting or shortcuts changes, because the operating system and third-party libraries can behave in ways a mock does not show.
